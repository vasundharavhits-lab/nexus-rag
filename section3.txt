1. Version-aware retrieval
Problem. The workspace holds several versions of the same document (architecture_v1.md, architecture_v2.md, architecture_v3.md). Plain similarity search treats them as unrelated files. A question such as "What is the currently approved architecture?" can therefore return chunks from all three versions, and the model may mix them or answer from an outdated one.
Method. Each document carries metadata: a version label, an approval status and an effective date. Before retrieval results reach the model, the system reads the question and classifies its version intent:
Current ("currently", "latest", "most recent"): for each document family, keep only the best current version, preferring approved over draft and then the newest date. Older versions of the same document are dropped.
Named ("in v1", "in version 2"): keep only chunks from that version.
None: leave the results unchanged.
The decision is recorded in the response trace (intent, named, dropped), so a reader can see which files were removed and why. The prompt also gives the model each source's version, status and date, so it can state which version it is describing.
Related fix: metadata-only chunks. Some chunks contained only header lines such as Status: Approved and Date: 2026-03-20. They scored high on similarity but contained no answer. They are now filtered out before ranking.

Limitations.
The test has 7 questions about one multi-version document, and the questions contain explicit trigger words. It demonstrates the mechanism and does not measure how well it generalises.
Intent detection uses keywords, so a version question phrased without those words would be treated as intent "none".
The rule fixes which version is shown, but it does not fix retrieval noise. Some answers still include unrelated chunks, such as a test report, in the evidence.

2. Refusal gate and the 0.60 threshold
Problem. If the best retrieved chunk is only loosely related to the question, a small model such as qwen2.5:3b can still produce a fluent answer from it. The system needs a rule for refusing when the evidence is too weak.
Method. Before calling the model, the system checks the similarity score of the best chunk. If it is below MIN_VECTOR_SCORE (0.60), the model is never called. The response is insufficient_evidence, with a message that names the nearest passages so the user knows where to look. The threshold and the score are both stored in the trace (gate_threshold, gate_vector_score).
Two bugs found and fixed. Both made the gate look better than it was.
Status-only chunks inflated the score. A chunk containing only Status: Approved and a date scored 0.8445 and passed the gate, but the model never saw it. The best chunk the model actually received scored 0.5441. These chunks are now filtered out before the gate is computed.
The gate was computed before the version rule. For "How does the current architecture handle ingestion?" the gate read 0.7607 from a chunk that the version rule then dropped, while the best chunk the model saw scored 0.7146. The gate is now taken from the final rows, after filtering and version selection.
Because of the first bug, the threshold had to be re-measured. The earlier sweep was run on inflated scores and is discarded.

Which questions are refused wrongly. The two missed benchmark questions are paraphrases: "Which design shipped everything as one deployable unit?" (0.534) and "Which release moved document processing into a background component?" (0.573). They describe an idea without the document's own words, which the embedding model scores lower.
Limitations.
The sample is small (30 and 8 questions), and the threshold was tuned on the same questions it is measured on, so 28/30 and 8/8 are optimistic. A held-out set would be needed for an unbiased figure.
Broad version questions are refused. On the real query path, 3 of 7 version questions fall below 0.60: "What is the currently approved architecture?" (0.544), "Which architecture design is the most recent?" (0.513) and "What does version 3 add to the architecture?" (0.578). Each chunk covers only one part of the architecture, so no single chunk matches a question about the whole. The highest unanswerable score (0.574) overlaps these, so no single cutoff separates them. A single top-1 similarity score cannot tell "broad question with evidence spread over several chunks" from "no evidence". A possible mitigation is to base the gate on the top two chunks for such questions, which I have not tested.
The hybrid route's gate is computed separately and was patched to ignore status-only chunks, but it does not use the final rows after the version rule, so it can still differ from what the model sees.



3. Claim-level verification
Problem. The citation check from the earlier weeks only asks whether the answer contains a valid [n]. It never checks that source [n] actually says what the sentence says. In one real answer, the model wrote a single sentence naming PostgreSQL with pgvector, Redis, a reranking stage and Celery workers, and cited only source [3]. I read the two chunks: [3] covers the reranking stage and Celery, while pgvector and Redis appear only in source [2]. All four facts were true, but two were attributed to the wrong source. The system still marked the answer answered.
Method. Each answer is split into sentences, and the citation markers are removed. Every sentence is then checked against every retrieved source with a small natural-language-inference (NLI) model (cross-encoder/nli-deberta-v3-small), which gives the probability that the source entails the sentence. A source supports a sentence when that probability is at least 0.5. Each sentence gets one verdict:
supported: at least one cited source supports it.
wrong_source: a cited source does not support it, but another retrieved source does. The better sources are listed.
unsupported: no retrieved source supports it.
The result is returned in a verification field. It only reports. It does not change status and never blocks an answer. If the checker fails, the answer is returned with an error note instead.
Choice of checker. I chose a dedicated NLI model over asking qwen2.5:3b to judge. A 3B model is an unreliable judge, which would make the check itself hard to trust. The NLI model is also faster, since a judging call on this CPU would add roughly 15 to 25 seconds per check.
Two bugs found while testing.
Removing [3] left a space before the period (stage .). That alone dropped the score for a true claim from 0.99 to 0.24. The marker is now removed together with the space before it.
The model sometimes places the citation after the period (retrieval. [1]), which split the answer into a claim without a citation and a stray fragment. The sentence splitter no longer breaks before a bracket.

Limitations.
The sample is small and easy. The 4 real claims were short paraphrases of a single chunk, which is what the checker handles best. This shows the mechanism works, not how often it is right.
The small NLI model is fragile with some phrasings. "The system adds a reranking stage" scored 0.31 against a source that says exactly that, and a sentence starting with "It" scored 0.01. These would show up as false alarms on true answers.
A sentence that combines facts from two sources, such as the original four-claim sentence, scores 0.00 against every single source and is reported as unsupported, when the real problem is mixed attribution. Splitting compound sentences into smaller claims would address this. I did not build it.
The verifier reports only. A client has to read the per-sentence verdicts, and there is no overall verified flag.
It adds time to each answered response (the full cost has not been measured separately from generation time). Loading the model on the first call is slower.
