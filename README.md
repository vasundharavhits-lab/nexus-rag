# Nexus RAG

A small retrieval-augmented question answering system for technical project documents. It ingests Markdown, DOCX and PDF files, keeps version and provenance metadata, retrieves evidence, and answers with citations. It refuses to answer when the evidence is too weak, and it checks each answer sentence against the sources.

## What it does

- Upload documents into a workspace. Corrupted, empty and duplicate files are detected and reported.
- Chunk documents by structure (headings, paragraphs) and index them for vector and keyword search.
- An automatic router chooses vector search or hybrid search (keyword + vector, merged with Reciprocal Rank Fusion) for each question.
- Version rule: questions about the "current" version keep only the newest approved version; questions naming a version ("in v3") keep only that version.
- Refusal gate: if the best chunk scores below 0.60 similarity, the model is not called and the answer is `insufficient_evidence`.
- Answers are generated by a local model (Ollama, `qwen2.5:3b`) and must cite sources like `[1]`.
- A claim verifier (NLI model) reports, per sentence, whether the cited sources support it. It reports only and never blocks an answer.

## Requirements

- Windows, macOS or Linux with Python 3.11 or newer (developed on Python 3.14)
- PostgreSQL (the pgvector extension is not required)
- [Ollama](https://ollama.com) with the model `qwen2.5:3b`
- About 2 GB of disk space for the Python packages and the embedding and verification models, which are downloaded on first use

## Setup

1. Create and activate a virtual environment:

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
```

2. Install the packages:

```powershell
pip install -r requirements.txt
```

3. Create the database. Replace the password and use the same one in the next step. No PostgreSQL extensions are needed.

```sql
CREATE USER nexus WITH PASSWORD 'your_password';
CREATE DATABASE nexus OWNER nexus;
```

4. Copy `.env.example` to `.env` and set your password:

```
DATABASE_URL=postgresql://nexus:your_password@localhost:5432/nexus
```

`.env` holds secrets and is excluded from Git by `.gitignore`. Optionally set `LLM_MODEL` to use a different Ollama model.

5. Download the language model:

```powershell
ollama pull qwen2.5:3b
```

6. Start the server (Ollama must be running):

```powershell
uvicorn app.main:app --reload
```

Open http://127.0.0.1:8000/docs for the interactive API page.

## Using the API

All requests need the header `X-User-Id` (any string; each user only sees their own workspaces).

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/v1/workspaces` | Create a workspace |
| POST | `/api/v1/documents/upload?workspace_id=...` | Upload a file |
| POST | `/api/v1/workspaces/{id}/index` | Build the search indexes |
| POST | `/api/v1/query` | Ask a question (`mode`: `auto`, `vector`, `keyword`) |
| GET | `/api/v1/runs/{id}` | Inspect a past run: evidence, trace, timings |
| GET | `/api/v1/chunks/{id}` | Read the exact cited passage |
| POST | `/api/v1/feedback` | Rate a past run (thumbs up or down, issue type, comment) |
| GET | `/api/v1/analytics/retrieval?workspace_id=...` | Run statistics: status rates, routes, median timings, feedback counts |

A query response contains `status` (`answered`, `uncited`, or `insufficient_evidence`), the `answer`, `citations`, `evidence`, a `trace` (route, version decision, gate score and threshold, timings) and a `verification` field with per-sentence verdicts.

## Tests and evaluation

Run the automated tests (expected: 52 passed):

```powershell
pytest -v
```

Abstention test on the 13 sample documents (5 unanswerable and 10 answerable questions; needs Ollama running):

```powershell
python -m scripts.eval_abstain data\raw
```

Prompt-injection test (a document that contains a hidden instruction):

```powershell
python -m scripts.eval_injection
```

Questions are in `eval/`, and saved results (ablation, benchmark, ingestion quality) are in `reports/`.

## Demo scenario

1. Create a workspace and upload everything in `data/raw`. Index it. The broken PDF is rejected and recorded, and the duplicate files are flagged.
2. Ask `What causes ERR-5023?` (auto mode). The router picks hybrid search and the answer cites `incident_log.md`.
3. Ask `Why was DR-002 decided?`. The answer cites the decision record.
4. Ask `What is the currently approved architecture?`. Open the `trace`: the `version` field lists the older files that were dropped.
5. Ask `Who is the CEO of the company?`. The system answers `insufficient_evidence` and names the nearest passages instead of inventing an answer.
6. Open the `verification` field of an answered query to see each sentence marked supported or not.

## Results summary

- Structure-aware chunking gave a clearly better MRR than fixed-size chunks (0.90 against 0.73). Hybrid search and reranking did not beat plain vector search on this small corpus.
- Abstention: 5 of 5 unanswerable questions refused, 1 of 10 answerable questions wrongly refused.
- A hidden "ignore previous instructions" line in a document did not change the answer.

Full tables and limitations are in the report (`Nexus_RAG_Weeks_7-12.docx`).

## Known limitations

- The corpus is small (13 documents), and the system was tuned on questions similar to the test questions, so the scores are probably optimistic.
- The 0.60 similarity gate can refuse short, vague questions such as "What changed in v3?".
- Answers shorter than 3 words besides the citation are marked `uncited` even when they contain a citation.
- Version detection uses keywords, so a version question without trigger words is treated as having no version intent.
- The verifier can raise false alarms on true answers and cannot handle sentences that combine facts from several sources. Its time cost has not been measured.
- The prompt-injection test covers one document and one attack.
